The method stays narrow. The evidence gets stronger.

Done Means follows a fixed sequence so a project review cannot silently become generic cleanup or a second task system.

  1. 1
    Read the live project

    Inspect instructions, manifests, configuration, source, tests, and current Git state.

  2. 2
    Define DONE MEANS

    Write three to six independently verifiable conditions before deriving work.

  3. 3
    Classify the gap

    Use only BROKEN, MISSING, or REQUIRED findings with a real citation.

  4. 4
    Sequence the work

    Split tasks until they fail independently, then order them by dependency.

  5. 5
    Verify the outcome

    Recheck every condition independently. Stop honestly at a real blocker.

Questions worth answering.

Does it require Airtable?

No. The public package does not assume Airtable or any fixed account. Use the project’s named backend or request the local Markdown fallback.

Does it create generic tasks?

No. Tasks must trace to a finish-line condition and carry evidence classified as BROKEN, MISSING, or REQUIRED.

Can it execute the roadmap?

Yes, when execution is explicitly requested. It performs safe local work, verifies outcomes, and stops at approval, credential, access, safety, or external-system boundaries.

What counts as evidence?

A path and line, a command and observed error, or an explicit absence. A prior report or successful file write is not proof by itself.

Can a project already be complete?

Yes. If every finish-line condition passes current independent checks, the correct result is complete with no manufactured backlog.

Define the finish line. Keep the evidence. Ship with proof.
